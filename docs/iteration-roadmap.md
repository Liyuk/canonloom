# CanonLoom 迭代路线

当前 P0/P1 的目标是让协议、门禁、状态、上下文和结算可靠闭环。P2 不默认全部启用，而是按项目规模和失败类型选择。

## P2-A：状态检索层

为事件、知识和揭示建立轻量索引，按当前章节的角色、地点、时间、章契引用筛选上下文。适合章节超过 30 章、canon 文件开始明显变大时。建议先做 SQLite/JSONL 索引和可解释检索，不直接引入复杂知识图谱。

## P2-B：因果与角色状态检查

把 `causal_change`、`character_agency` 和事件状态变成可比较的前后快照，检查角色是否有目标、选择和代价，章节出口状态是否改变，新事件是否违反时间线或世界规则，以及角色是否获得没有来源的能力或信息。

建议先做规则型检查，再让 Agent 解释冲突，不直接自动改正文。

## P2-C：审查质量校准

记录 Finding 在作者审阅后的结果：误报、漏报、已接受风险和实际修复效果。运行多个章节后，可以缩短低价值 review，降低 token 和时间成本，但不能把单一分数当作文学质量。

## P2-D：作者引导命令

在不做 GUI 的前提下增加少量高层命令，例如 `canonloom start idea`、`canonloom start planning`、`canonloom start work` 和 `canonloom inspect chapter-012`。命令只生成下一步提示和任务文件，不隐藏阶段，也不替作者批准。

## P2-E：可选多模型审查

多模型只用于隔离的高风险复核，例如时间线、版权相似性或终稿审查。不得共享可变隐式记忆，也不得把不同模型的建议直接合并进 canon。默认仍然使用“单一模型创作线程 + Python 确定性工具 + 独立审查 pass”。

## P2-F：原创 benchmark

建立不含既有小说上下文的公开小型数据集，固定项目种子、章契、模型版本、token、延迟、重试、作者修改时间，以及连贯性、因果性、角色能动性和读者效果的人评。至少运行多个题材和章节，报告均值、方差和失败案例。

## 推荐顺序

```text
P2-A 状态检索
  → P2-B 因果/角色检查
  → P2-C 审查校准
  → P2-D 作者命令
  → P2-E 多模型复核（可选）
  → P2-F benchmark 持续化
```
