# CanonLoom 0.2.1：一个命令驱动、作者掌舵、可审计的长篇小说生产框架

> 发布公告 · CanonLoom 0.2.1 · 2026-08-15
> 完整系统设计论文：[docs/paper-0.2.0/paper.md](../paper-0.2.0/paper.md)（0.2.0 定稿）

> **一句话总结**：CanonLoom 不解决"让模型写出更好的句子"，它解决的是——当一部小说写到第 40 章时，为什么第 3 章埋的线还在、人物的动机没有漂移、模型发明的设定没有悄悄变成"故事事实"。它把长篇小说生产从"一段不可追踪的提示词续写"，重新建模为**可恢复、可审计、作者批准每一步状态晋升**的生产流程。

---

## 为什么会有 CanonLoom

"帮我写下一章"——这是长篇创作里最自然、也最危险的一句话。

表面上它是一次文本生成；实际上它是一次**持续的状态管理**。作者脑子里的东西包括：人物动机、时间线、视角可见性、伏笔与揭示顺序、卷级目标、章级变化……这些状态如果藏在模型上下文里，几章之后就会以同样隐蔽的方式坏掉：

- **状态漂移**：角色目标、知识范围、世界规则在不同章节之间悄悄变化；
- **未批准的事实晋升**：模型随口发明的设定，因为写进正文就被当成"故事事实"；
- **审查不可追溯**：某句对话到底依据了哪份材料？这个审查意见修了吗？修完有没有引入新问题？——全都问不出来；
- **建议与决定混淆**：模型提的选项、Agent 的临时选择、作者的正式批准，三层混在一起，后续上下文把"建议"当成"事实"。

核心问题不是模型不够聪明，而是**状态、决策和验证边界没有显式化**。CanonLoom 的全部设计，就是把这几个边界一层一层划清楚。

## CanonLoom 是什么

CanonLoom 是一个**命令驱动、文件协议驱动的写作工作流**，不是 GUI 写作软件，也不是"一句话自动生成整本小说"的黑箱。

分工是这样的：

```text
作者        → 执行短指令、做选择、批准
Agent       → 读任务文件，负责创意、规划、写作、修订、审查解释
Python      → 负责确定性检查、索引、来源追踪、阶段门禁、运行记录
文件        → 作者意图、canon、计划、草稿、审查、状态、trace 全是可读文件
```

Agent 读取 `tasks/current.md`，把产物写进约定目录；Python 脚本负责所有"不能靠感觉"的部分；作者在每个关键节点做决定。**任何一层不依赖某个模型的隐藏记忆**——Codex、Claude Code、OpenCode 都能在同一套文件协议上工作。

## 核心设计：强约束 S0–S6

CanonLoom 把一章的生产拆成 S0–S6 七个阶段，阶段不能跳过：

```text
S0  Contract       冻结章契、方案选择和上下文包，验证合法性
S1  Draft          按通过契约生成候选正文
S2  Quick Check    确定性快速检查
S3  Repair         按 Finding 和证据做受限修订
S4  Strict Check   严格结构/连续性检查
S5  Independent Review  独立审查视角（报告独立，不等于必须用第二个模型）
S5b Cross-Validation    对两份隔离报告交叉验证
S6  Settlement     作者批准，正文进入 manuscript、状态结算
```

每条规则背后都是同一个原则：**候选不是决定，草稿不是定稿，审查意见不是事实，状态晋升必须经过作者批准**。

>S6 没有作者批准文件时，系统不会把草稿晋升到 `manuscript/`；叙事状态也不会自动变成 canon。强约束限制的是状态边界，不是每个句子的表达——文学层面的新意仍然属于生成器和作者。

## 章契不是摘要，上下文不是全文

**章契（chapter contract）**不止描述"本章写什么"，它至少描述：

- 必须发生的变化与禁止发生的变化；
- 每个 Beat 的参与角色、动作、冲突和出口；
- 因果变化：什么条件导致什么结果；
- 角色能动性：谁做出不可替代的选择；
- 读者效果：应该产生的问题、压力和情绪变化；
- 揭示更新：哪些可以揭示、哪些必须继续隐藏；
- 章节出口状态：下一章可继承的事实和开放问题。

**上下文编译**把当前任务需要的材料打包成有边界的 context package，并记录每一份来源文件的 SHA-256 指纹、包含/排除项和选择原因。它不塞整本书进提示词，也保证"这段正文依据了什么"是可检查的。

## 可选叙事状态层

当作品复杂到需要时，可以启用三样状态文件：

- **事件**：发生了什么（planned / proposed / confirmed / rejected）；
- **知识状态**：谁在什么时间点知道哪些事实（防止视角角色使用尚未获得的信息）；
- **揭示与伏笔**：setup → promise → reveal → payoff 的追踪。

它默认可选，支持 `disabled / optional / required` 三种模式——不强迫每个项目一开始就上复杂知识图谱。

## 实际效果：现在能确认什么

必须把话说清楚：**CanonLoom 现在验证的是"工程可靠性"，不是"写出来的小说质量更高"**。没有采集到的数据，不会当成结果来写。

当前可复现的验证包括：

- **18 项 Python 单元测试通过**，覆盖命令、协议、配置优先级、状态验证和公共入口等核心路径；
- **最小项目 smoke 通过**：`init → setup → idea → diagnose` 全链路可跑通，产出合法的任务文件和协议产物；
- **本地确定性工具耗时实测 183 ms**（一章草稿、6 个工具步骤：beat 校验、quick/strict 校验、索引、style、stats），不含模型调用耗时——说明 Python 层在创作流程里通常远小于一次模型请求；
- **S0–S5b 章节工作流在外部测试项目上可完整走通**，生成状态验证和审查产物；
- **每次运行记录 manifest**：阶段、工具调用、输入/输出 token、延迟、重试、事件，上下文包与章节索引记录来源文件的 SHA-256 指纹。

论文第 10 节给出了一套**可复现的受控实验协议**（固定模型/seed/章契/输出预算，比较单提示、提纲路径、结构化单路径、CanonLoom 各档，报告一致性、因果、能动性、知识泄露、揭示控制、token、延迟、重试和作者负担），质量对比要等这组实验跑完，才能从"架构设计"升级为"已验证的叙事生产架构"。

### 你也可以 5 分钟跑通

不依赖任何第三方包，只要 Python 3.9+：

```sh
git clone <your-canonloom-repo>
cd canonloom

./bin/canonloom init ~/my-novel --name "My Novel"
./bin/canonloom --root ~/my-novel setup --confirm   # 确认作者配置
./bin/canonloom --root ~/my-novel idea              # 开始创意
./bin/canonloom --root ~/my-novel continue          # 按 next_action 继续
```

`init` 之后先完成 `setup`：作者配置题材、受众、视角、文风方向和内容边界；Agent 把已有材料识别成候选人物、世界、线索和技法——**作者配置与 AI 识别分开保存，AI 推断不会自动进入 canon**。

跑一遍 `minimal-project` 里的 `smoke.sh` 也能看到完整的最小链路。作者日常最常见的命令：

```sh
./bin/canonloom --root ~/my-novel status       # 现在处于什么阶段？
./bin/canonloom --root ~/my-novel continue     # 按 next_action 继续
./bin/canonloom --root ~/my-novel diagnose     # 检查结构和状态
./bin/canonloom --root ~/my-novel repair       # 修复安全的结构问题
./bin/canonloom --root ~/my-novel state report # 汇总可选叙事状态
```

## 一些设计上的"不"

与很多项目不同，CanonLoom 明确不做什么，这本身就是一种取舍：

- **不是 GUI 编辑器**，不把作者变成界面里的操作员；
- **不默认多模型/多 Agent**——默认是"单一主模型 + Python 确定性工具"，多模型只作为隔离审查的可选实验，避免上下文重复发送和状态分叉；
- **不引入图数据库作为默认依赖**——早期项目的主要问题通常不是查询性能，而是状态定义、来源和批准边界还没稳定；
- **不把"token 更少"或"分数更高"解释成文学质量**——质量至少要在 7 个维度上分开报告（连续性、因果、章契遵循、角色能动性、读者承诺、风格、作者负担）；
- **不自动出版、不承诺不经人工评审就能发布作品**。

## 下一步

论文第 16 节说得最准确：

> CanonLoom 0.2.0 把长篇小说人机协作从一次性的提示词活动，重新表示为一个可恢复的生产流程。当前版本已经具备可运行的工程骨架和基础验证，但还没有完成能够支持文学质量优越性结论的公开受控 benchmark。下一步最重要的不是继续堆叠 Agent，而是建立原创、可复现、包含人工盲评的长篇一致性数据集。

对读者来说，CanonLoom 现在值得一看的是：**它把"长篇一致性到底坏在哪"和"哪些部分可以用确定性工具管住"这两件事，用一个可以跑起来的工程说清楚了。** 如果你是长篇作者、Agent 工作流研究者，或对"人机协作的边界"感兴趣，欢迎打开仓库跑一遍最小示例，或者读那篇 0.2.0 论文。
