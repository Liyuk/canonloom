长篇小说生产框架，
把写作变成可恢复的状态机

CanonLoom 不是"一句话生成整本小说"的黑箱。它把一章的生产拆成 S0–S6 七个强约束阶段，作者在每一步做选择与批准，Python 做确定性校验， Agent 负责创作。协议在文件里，不在模型的记忆里。

一章的生产：从想法到结算，阶段不能跳过

每一章都要走过 S0–S6。任何一层不依赖某个模型的隐藏记忆——出问题可以定位到具体阶段。

  1. S0 章契 冻结章契、方案选择、上下文包
  2. →
  3. S1 草稿 按通过契约生成候选正文
  4. →
  5. S2 快速检查 确定性快速校验
  6. →
  7. S3 修订 按 Finding 受限修订
  8. →
  9. S4 严格检查 结构 / 连续性检查
  10. →
  11. S5 独立审查 独立审查视角
  12. →
  13. S5b 交叉验证 隔离报告交叉验证
  14. →
  15. S6 结算 作者批准 → 进 manuscript

S6 没有作者批准文件，草稿就不会晋升到 manuscript/。阶段不能跳过，状态晋升必须经过作者。

它解决什么问题

长篇小说最容易坏在章节之间：人物动机漂移、时间线断裂、未经批准的设定悄悄变成"故事事实"。

🧭

状态漂移

角色目标、知识范围、世界规则在不同章节之间悄悄变化。状态显式化为文件后，漂移可以被检测。

📄

未批准晋升

模型随口发明的设定，写进正文就当成了"故事事实"。S0–S6 门禁保证候选不是决定。

🔎

审查不可追溯

"这段依据了哪份材料？这条审查意见修了吗？"——上下文包记录每份来源的 SHA-256 指纹。

✋

建议与决定混淆

AI 选项、Agent 临时选择、作者正式批准三层分开保存。AI 推断不会自动进入 canon。

作者意图 → 章契 → 草稿 → 评审

创意走创造性环路（发散 → 比较 → 选择 → 创作），约束走治理环路（取回 → 校验 → 审查 → 结算）。

作者日常只需要一套短命令

~/my-novel
$ ./bin/canonloom init ~/my-novel --name "My Novel"
✓ project initialized (0.2.1)
$ ./bin/canonloom --root ~/my-novel setup --confirm
✓ AUTHOR_SETUP_CONFIRMED
$ ./bin/canonloom --root ~/my-novel idea
→ generated 3 candidate directions
   [1] a locked room and an unreliable witness
   [2] ...
$ ./bin/canonloom --root ~/my-novel status
STAGE: ideation · next_action: Start ideation
LANGUAGE: en · WORKFLOW: standard
$ ./bin/canonloom --root ~/my-novel continue
✓ current.md updated — agent reads tasks/current.md
$ ./bin/canonloom --root ~/my-novel diagnose
✓ structure OK

命令只负责准备可读的任务文件。Agent 读取 tasks/current.md，执行任务并把产物写入约定目录。

  • status — 现在处于什么阶段？
  • continue — 按 next_action 继续（最常用）
  • diagnose — 出问题时先跑这个
  • repair — 修复白名单内的结构问题
  • state report — 汇总可选叙事状态

设计上的"不"

不是 GUI 编辑器

不把作者变成界面里的操作员。

不默认多模型

单一主模型 + Python 确定性工具，避免状态分叉。

不引入图数据库

早期项目的主要问题不是查询性能，而是状态边界。

不把数字当质量

"token 更少"或"分数更高"不等于文学质量。

五分钟，跑通最小链路
